# 先有结果的项目怎么进流程

很多项目是实验跑完了才来写论文。这是常态，不是例外；流程为它留了事后入口；内部记录如实，正文按普通论文的做法交代（见下文）。"包装"在这里的合法含义是：找到现有证据能回答的问题、选对读者、排好顺序、定好图一。不合法的含义是：把事后选择写成事前设计、挑格子、换分母、拿旧基线对照、藏阴性。

## 已有自己文件布局的项目

很多这样的项目早有一套文件：framing 写在 `paper/latex/` 下某个名字里，台账是一个 markdown 表，各阶段的结果散在 `stages/` 下。不要为了对齐模板改名、搬文件或生成一套空模板，那会弄乱现有脚本与证据链。只建两份状态文件（`init_paper_project.py <目录> --state-only`），在 `research/STATE.md` 的阶段产出索引里写 `默认路径 → 实际路径`，`check_gates.py` 就按索引找；"当前阶段"按产物实际到达的阶段填，"阶段历史"写明哪些阶段是接入前完成、本次按产物回填。写法见 [state-template.md](state-template.md)。

## 五步

1. **冻结现状。** 清点所有运行、输出、脚本与配置；给现有脚本算哈希；用 orchestrator 的状态值给每条结果分类（`VERIFIED_CURRENT` / `CONTROLLED_OR_RETROSPECTIVE` / `EXPLORATORY_OR_CANDIDATE` / `SUPERSEDED_OR_INVALID` / `MISSING_OR_UNRESOLVED`）；重建时点：哪些决定是看过 dev 或 test 之后做的，test 是否被触碰，看过多少配置。不知道就写"时点未知"。
2. **事后 R1。** 用 `paper-framing` 的事后模式：恢复证据与选择历史、从观察走向有用问题、区分解释、核实最近工作差异、锁定主张。FRAMING 的产生时点写"事后"，并列出曾考虑过的其他主线及放弃的理由；评审 skill 的 framing A/B 做的正是这件事。骨架只从 `VERIFIED_CURRENT` 的证据里长出来；分支已由结果决定，结算在此一并完成：骨架按带分支的模板写好后另存一份 `paper/STORY_SPINE_R1_<date>.md`（内容相同即可），再在原文件写结算节，R3 门槛对事后项目同样要求这份归档。
   **正文怎么交代时点（按普通 SE/安全期刊的做法）。** 正文不逐条标"事前 / 事后"，不贴 post hoc / retrospective 标签，也不因为项目是先做实验后写论文就整篇降级。审稿人实际看三件事：方法和参数在开发集上定，没拿测试集调；结论不超过证据量（单次运行、样本少照实写）；正文没出现的早期版本在同一测试集上评过、新方法的想法来自早期版本的错误，属于普通研究过程，不用写进论文。后来补做的分析在正文里叫"分析"，不说成"验证"。内部记录（FRAMING 的产生时点、选择史、RESULT 的事后分析节）照常保留备查，不作为降级依据。
3. **确认运行是可选的加强项，不是必须。** 只有当主要比较或配置确实是看着测试结果挑出来的，才建议在未触碰的材料上（新样本、新对象、新时间段，量化实验里是新种子或新划分）再跑一次，这是一个小的 R2 到 R3；不跑也可以投，正文按上面的普通做法写，结论不超过证据量。做不做由潜力卡和用户的授权决定。确认协议之前照常可以做试点，但试点不能再碰已被用来选主比较的数据。
4. **从现有输出生成台账。** 证据台账与主张台账直接从输出文件生成；没有输出文件支撑的数字不进正文。回顾性的协议文件把实际做了什么如实写下，不冒充事前冻结；这是内部记录，正文不需要这个标签。
5. **正常进入 R4。** 先图后文；不需要逐条标时点，也不用交代测试集的使用史。

## 可以做与不可以做

| 可以做 | 不可以做 |
|---|---|
| 选证据能回答的问题，收窄主张 | 把事后 RQ 写成预先设定 |
| 选读者、定顺序、定图一 | 从多种配置里挑最好的那格当主结果 |
| 把非中心结果按陈述的规则放附录 | 换分母、换评分规则、删不利的运行或样本 |
| 用已验证范围内的构念命名问题 | 用旧基线对照当作对当前方法的优势 |
| 如实写单次运行、单个案例 | 把单次运行的增益写成稳定提升 |

## 门槛

事后入口的 R1 门槛与常规相同，多一条：每个进正文的数字能追到现有输出文件。选择史建议写进 FRAMING 备查，不是门槛。`check_gates.py` 对事后项目不做特殊处理，产生时点写"事后"即可通过格式检查；文件不在默认位置的按 STATE.md 的阶段产出索引找，内容要求不变。
