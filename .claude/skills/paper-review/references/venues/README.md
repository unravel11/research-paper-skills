# venue 档案

核心量表不为任何 venue 定制；venue 之间的差别全放在这里。一个 venue 一个文件，文件名是小写缩写，如 `tse.md`、`icse.md`。本仓库不内置档案，每个 venue 由使用者按下面的模板自建。评审时按 `paper/VENUE_PROFILE.md` 的决定或用户指定的缩写加载；没有档案就用通用量表并建议建档。

档案与 research-pipeline 的 `paper/VENUE_PROFILE.md` 分工：VENUE_PROFILE 是某篇论文对候选 venue 的记录（读者、属性、分支去向、决定）；这里的档案是评审 skill 对一个 venue 的长期知识，所有论文共用。

## 新建档案的模板

```markdown
# <缩写>：<全称>

## 基本信息
- 类型：期刊 / 会议；出版方：
- 官方来源（validator 用作前缀；只填官方页面）：
  - 主页：
  - 作者指南 / Call for Papers：
- 研究类型与对应的经验标准（ACM SIGSOFT Empirical Standards 的哪几份）：

## 读者与奖励的贡献类型
- 读者是谁、现在怎么做：
- 奖励：方法 / 测量 / 实证规律 / 资源 / 阴性与边界 / 应用 / 形式化
- 不奖励或常被拒的类型：

## L1-G6 的适配问题
- （三到五个只对这个 venue 成立的问题）

## 附加门（ID 用缩写做前缀）
### <缩写>-G1 <名称>
（这个 venue 独有的、核心门没覆盖的要求；每门写判定标准）

## L3 scope 核对项
- （按当前官方材料核对的条目；写明去哪个页面查）

## 这个 venue 常见的不允许升格
- （例如：把受控环境的结果写成真实部署；把同池比较写成端到端）
```

## 维护规则

- 官方 URL 变了就更新，并在 CONTEXT.md 记一行；排名、费用、周期不写进档案，评审时按官方来源协议现查。
- 附加门只收核心门真的没覆盖的内容；能并进核心门的不要新开。
- 一个 venue 的档案不套到另一个 venue。安全会议没有档案时，另读 orchestrator 的 `security-venue-review.md`。
