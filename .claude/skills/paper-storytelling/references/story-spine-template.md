# 故事骨架模板

写入 `paper/STORY_SPINE.md`。R1 写第一版：读者、原信念、张力不依赖结果，先写死；转折、收获、一句话故事按分支各写一版，每个分支各做删除测试、各写适合的 venue 候选。R3 之后做结算：把 R1 版本复制为 `paper/STORY_SPINE_R1_<date>.md` 归档，在"结算"节按台账选定一个分支，落实决定只按选定分支填。每项不超过两句；每项后面括号注明依据（台账证据 ID、文献键或"待核实"）。

```markdown
# Story spine

- 读者：
- 原信念 / 现做法：（依据：）
- 张力：（依据：）

## 分支 A：主要比较成立
- 转折：（依据：证据 ID，R1 时写"待 R3"）
- 收获与边界：
- 一句话故事（≤40 字）：
- 适合的 venue 候选：
- 删除测试：删除中心主张后章节顺序是否需要变：是 / 否（否 = 骨架未抓到）

## 分支 B：主要比较不成立
- 转折：
- 收获与边界：
- 一句话故事（≤40 字）：
- 适合的 venue 候选（退路）：
- 删除测试：删除中心主张后章节顺序是否需要变：是 / 否（否 = 骨架未抓到）

## 分支 C（可选）：混合或条件性成立
- 转折：
- 收获与边界：

- 适合的 venue 候选：

## 落实决定（结算后按选定分支填写）
- 标题候选：

  - RQ1：

- venue 决定：见 paper/VENUE_PROFILE.md
```

分支 C 可以删掉不填；填了就同样要过删除测试。`research-pipeline/scripts/check_gates.py` 只检查填写了一句话故事的分支，要求至少两个。

## 示例（虚构，只为说明写法）

题材是虚构的：用一个轻量分类器先筛掉"肯定不是 flaky"的测试失败，把重跑留给真正含糊的那些。R1 时两个分支写得同样具体，证据 ID 指向台账里尚不存在的行，R3 之后只有一个分支会被结算。

- 读者：维护大型 CI 的团队，每天要决定哪些失败值得重跑。
- 原信念 / 现做法：判断一个失败是不是 flaky 必须重跑多次；重跑是必要成本。（依据：文献键 [1][2]，现行 CI 默认策略）
- 张力：重跑占 CI 时间的大头，而多数失败并不含糊，一眼就能定。（依据：待 R3 的失败分布统计，E-01）

分支 A（主要比较成立）：
- 转折：一个只看失败日志与变更范围的轻量分类器，能把明确的失败先筛掉，重跑量减半而漏检率不升出非劣界。（依据：待 R3，E-07、E-12）
- 收获与边界：重跑预算可以省一半；只在 Java / JUnit 仓库上验证；分类器需要每个仓库约几百条标注。
- 一句话故事：多数失败一眼能定，重跑只留给含糊的那些。
- 适合的 venue 候选：面向工程团队的实证期刊。

分支 B（主要比较不成立）：
- 转折：分类器分不开"明确"与"含糊"，减少重跑就会放过真 flaky。（依据：待 R3，E-07 落在非劣界之外）
- 收获与边界：不要指望静态特征替代重跑；省时间要从并行重跑和失败去重找。
- 一句话故事：失败看起来明确，其实分不开，重跑省不掉。
- 退路 venue：同一读者的经验报告或工具论文；阴性结果要配结果中性检查，证明不是实现问题。
